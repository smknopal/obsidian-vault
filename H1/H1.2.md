## 3. Apa Itu Windows Event Log?

Windows mencatat berbagai aktivitas sistem sebagai **event**. Setiap kali sesuatu terjadi — seseorang login, sebuah proses dijalankan, sebuah service diinstal, sebuah akun dibuat — Windows berpotensi mencatatnya sebagai satu entri event.

Event-event ini disimpan dalam **channel** atau **log** tertentu. Setiap event memiliki timestamp, Event ID, provider, nama komputer, dan data tambahan (event data) yang menjelaskan detail aktivitas tersebut.

Fungsi utama Event Log dalam investigasi adalah membantu menjawab empat pertanyaan dasar:

- **Siapa** yang melakukan aktivitas?
- **Apa** yang dilakukan?
- **Kapan** dilakukan?
- **Di mana** (host/sistem mana) dilakukan?

Dua hal penting yang wajib dipahami sejak awal:

**WAJIB PAHAM**
> Tidak semua aktivitas otomatis tercatat. Logging bergantung pada konfigurasi audit policy dan fitur apa saja yang aktif di sistem tersebut. Sistem dengan audit policy default akan mencatat jauh lebih sedikit dibanding sistem yang dikonfigurasi khusus untuk security monitoring.

Beberapa istilah dasar yang harus dibedakan sejak awal:

| Istilah | Penjelasan |
|---|---|
| **Event** | Satu catatan aktivitas tunggal di dalam log. |
| **Event ID** | Nomor yang mengidentifikasi jenis aktivitas, **dalam konteks provider tertentu**. |
| **Provider** | Komponen software yang menghasilkan event (misalnya Microsoft-Windows-Security-Auditing). |
| **Channel** | Tempat event dikategorikan dan disimpan (misalnya Security, System). |
| **EVTX** | Format file Windows Event Log modern (`.evtx`). |
| **Record ID** | Nomor urut record di dalam satu file log tertentu. |

Satu Event ID **sendirian belum tentu cukup** untuk memahami sebuah event secara utuh — ia harus dibaca bersama provider, channel, dan field-field di dalamnya. Konsep ini akan dijelaskan lebih detail di bagian 5.

## 4. Log dan Channel Utama

### Security

Log Security umumnya berisi:

- authentication (login, logoff);
- account management (pembuatan, penghapusan, perubahan akun);
- group modification;
- privilege use;
- process creation — **jika** audit policy untuk Process Creation diaktifkan;
- audit policy change;
- log clearing.

**FALSE POSITIVE / KETERBATASAN**
> Kelengkapan log Security sangat bergantung pada audit policy yang aktif di sistem tersebut. Sistem dengan audit policy minim tidak akan mencatat banyak hal yang tampak "wajar ada" di kompetisi atau lab yang sudah dikonfigurasi khusus.

### System

Umumnya berisi service start/stop/install, driver, boot, shutdown, error sistem, dan perubahan komponen sistem. Event 7045 (service installed) berada di sini.

### Application

Berisi event yang dihasilkan oleh aplikasi pihak ketiga maupun komponen Windows non-security.

### Setup

Berkaitan dengan instalasi atau setup komponen Windows tertentu (feature update, komponen opsional, dan sejenisnya).

### Forwarded Events

Berisi event yang dikumpulkan dari sistem lain **jika** Windows Event Forwarding (WEF) digunakan pada environment tersebut. Tidak semua environment menggunakan WEF.

### Operational Logs

Beberapa komponen memiliki channel **Operational** khusus di bawah "Applications and Services Logs", misalnya:

- PowerShell (`Microsoft-Windows-PowerShell/Operational`);
- Task Scheduler;
- Windows Defender (`Microsoft-Windows-Windows Defender/Operational`);
- Terminal Services;
- Windows Firewall;
- WMI Activity.

**VERIFIKASI**
> Jangan mengklaim seluruh channel Operational di atas selalu tersedia atau aktif pada setiap sistem. Ketersediaannya bergantung pada versi Windows, fitur yang terpasang, dan konfigurasi audit/logging.

| Log/Channel | Fungsi | Contoh investigasi | Keterbatasan |
|---|---|---|---|
| Security | Authentication, account, group, privilege, log clearing | Siapa yang login dan kapan | Bergantung penuh pada audit policy |
| System | Service, driver, boot/shutdown | Kapan service diinstal (7045) | Tidak mencatat detail authentication |
| Application | Event aplikasi pihak ketiga | Crash atau error aplikasi terkait insiden | Formatnya sangat bervariasi antar-aplikasi |
| Setup | Instalasi komponen Windows | Perubahan komponen sistem | Jarang relevan langsung untuk serangan |
| Forwarded Events | Event dari host lain via WEF | Korelasi lintas host | Hanya ada jika WEF dikonfigurasi |
| PowerShell Operational | Script block & module logging | Isi command PowerShell | Perlu logging diaktifkan secara eksplisit |
| Defender Operational | Deteksi dan tindakan antivirus | Malware apa yang terdeteksi | Hanya mencatat apa yang dikenali Defender |

## 5. Provider dan Mengapa Provider Penting

Angka Event ID **dapat digunakan ulang oleh provider yang berbeda**. Artinya, Event ID yang sama pada dua provider berbeda bisa punya arti yang sama sekali berbeda. Karena itu, Event ID **harus** dibaca bersama:

- Provider;
- Channel;
- Timestamp;
- Field event data;
- Konteks investigasi secara keseluruhan.

Gunakan format identifikasi berikut setiap kali kamu mencatat sebuah event sebagai temuan:

```
Provider     : ...
Event ID     : ...
Channel      : ...
Computer     : ...
TimeCreated  : ...
Record ID    : ...
```

**COMBAT RULE**
> Jangan mengandalkan Event ID tanpa memeriksa provider dan channel. Kebiasaan ini akan menyelamatkanmu dari salah interpretasi saat lomba, terutama ketika evidence berasal dari export CSV yang sudah kehilangan sebagian konteks aslinya.

## 6. Anatomi Sebuah Event

Setiap event Windows (dalam format EVTX/XML) secara umum terdiri dari dua bagian besar.

### System Metadata

Bagian ini relatif konsisten strukturnya di semua event:

- Provider Name
- Event ID
- Version
- Level
- Task
- Opcode
- Keywords
- TimeCreated
- EventRecordID
- Channel
- Computer
- Execution ProcessID
- Execution ThreadID

### Event Data

Bagian ini **bervariasi tergantung jenis event**. Beberapa field yang sering muncul pada event investigasi:

- SubjectUserName, SubjectDomainName, SubjectUserSid
- TargetUserName, TargetDomainName, TargetUserSid
- IpAddress, IpPort
- WorkstationName
- LogonType, LogonProcessName, AuthenticationPackageName
- ProcessName, NewProcessName, ParentProcessName, CommandLine
- ServiceName, ImagePath
- TaskName
- MemberName, GroupName
- LogonId, ProcessId

Beberapa catatan penting:

- Tidak semua event memiliki semua field di atas.
- Nama field dapat berbeda antar-jenis event, meskipun secara konsep mirip.
- Field tertentu dapat kosong, `-`, atau berisi tanda pengganti (placeholder), tergantung konteks logon/proses.
- Raw XML membantu melihat nama field sebenarnya — ini penting karena parser tool tertentu kadang menamai ulang field.
- Parser tool tertentu dapat memindahkan sebagian data ke kolom generik seperti "Payload" atau "Details" jika tidak dikenali secara khusus.

| Field | Pertanyaan yang dijawab | Contoh pivot |
|---|---|---|
| SubjectUserName | Siapa yang melakukan aksi? | Cari login/aktivitas lain akun ini |
| TargetUserName | Siapa/apa yang terkena aksi? | Cari aktivitas akun target setelah kejadian |
| LogonType | Bagaimana cara login dilakukan? | Bandingkan dengan IP dan waktu |
| IpAddress | Dari mana koneksi berasal? | Cari event lain dari IP yang sama |
| LogonId | Session mana yang terkait? | Hubungkan logon → aktivitas → logoff |
| CommandLine | Apa isi perintah yang dijalankan? | Cari proses anak, file, atau koneksi jaringan |
| ServiceName / ImagePath | Service apa dan menjalankan file apa? | Periksa path dan proses terkait |

## 7. Subject versus Target

Bagian ini sering menjadi sumber kesalahan pemula, sehingga harus dipahami sangat jelas.

### Subject

**Subject** adalah akun atau konteks yang **melakukan** tindakan.

### Target

**Target** adalah akun, object, group, atau session yang **terkena** tindakan.

**Contoh fiktif 1**

Administrator membuat user `backupsvc`.

```
Subject : Administrator
Target  : backupsvc
```

**Contoh fiktif 2**

Administrator menambahkan `backupsvc` ke grup administratif.

```
Subject        : Administrator
Member/Target  : backupsvc
Group          : (nama grup administratif)
```

Penamaan field Subject/Target dapat sedikit berbeda tergantung jenis event (misalnya "Member" untuk event group management), tetapi konsepnya tetap sama: siapa pelaku, siapa/apa yang terdampak.

| Skenario                  | Subject                               | Target/Object       |
| ------------------------- | ------------------------------------- | ------------------- |
| User dibuat               | pembuat akun                          | user baru           |
| Password diubah/direset   | pelaku/perantara                      | account yang diubah |
| User ditambahkan ke group | pelaku                                | member dan group    |
| Login                     | konteks tertentu (mesin/proses logon) | account yang login  |

**KESALAHAN UMUM**
> Jangan menganggap field pertama yang muncul di layar selalu pelaku, dan jangan menganggap username pertama yang terlihat otomatis menjadi jawaban. Selalu cocokkan nama field-nya (Subject… vs Target…/Member…) sebelum menyimpulkan siapa pelaku sebenarnya.

## 8. SID, Username, Domain, dan Logon ID

### SID (Security Identifier)

Identifier keamanan unik untuk sebuah account atau security principal. SID tidak berubah meski nama akun diganti.

### Username

Nama account yang mudah dibaca manusia (human-readable). Bisa berubah sewaktu-waktu.

### Domain

Domain, hostname lokal, atau konteks account (misalnya `NT AUTHORITY`, nama domain AD, atau nama komputer untuk akun lokal).

### Logon ID

Nilai hexadecimal yang dapat digunakan untuk **menghubungkan event dalam satu session tertentu** pada satu host.

Keterbatasan yang wajib diingat:

- Username dapat berubah — SID lebih stabil sebagai identitas jangka panjang.
- Logon ID berguna untuk pivot **dalam satu host** pada rentang waktu tertentu.
- **Jangan menganggap Logon ID bersifat global** di seluruh host dalam environment — nilainya spesifik per host per session.
- Representasi nilai hexadecimal dapat tampil berbeda tergantung tool yang digunakan (misalnya dengan atau tanpa awalan `0x`).

Contoh alur pivot konseptual:

```
Username → SID → Logon ID → process → privilege → logoff
```

## 9. Logon Type

Logon Type menjelaskan **cara** sebuah logon terjadi. Field ini muncul pada event seperti 4624 dan 4625.

| Logon Type | Nama umum | Contoh penggunaan | Catatan investigasi |
|---:|---|---|---|
| 2 | Interactive | Login lokal melalui console | Periksa host dan user |
| 3 | Network | Akses share atau resource jaringan | Tidak selalu berarti RDP |
| 4 | Batch | Batch job | Dapat berasal dari scheduled task |
| 5 | Service | Service account start | Periksa service terkait |
| 7 | Unlock | Membuka sesi yang terkunci | Bukan login sesi baru penuh |
| 8 | NetworkCleartext | Credential dikirim ke package tertentu (mis. Basic Auth) | Perlu konteks tambahan |
| 9 | NewCredentials | RunAs /netonly atau credential baru untuk koneksi keluar | Perlu korelasi lanjutan |
| 10 | RemoteInteractive | RDP atau remote interactive lain | Periksa IP dan Terminal Services log |
| 11 | CachedInteractive | Login memakai credential cache | Umum saat domain controller tidak tersedia |

Tipe lain (misalnya Type 0/System) boleh disebut secara ringkas bila muncul, tetapi sembilan tipe di atas adalah prioritas untuk investigasi kompetisi.

**COMBAT RULE**

- Logon Type 3 **bukan otomatis** serangan jaringan — ini juga logon normal saat mengakses file share.
- Logon Type 10 **tidak sendirian** membuktikan RDP berbahaya — periksa IP, user, dan waktu.
- Service account dengan Type 5 **dapat normal** — banyak service Windows login dengan cara ini.
- Selalu periksa kombinasi user, IP, host, waktu, dan event lain sebelum menyimpulkan.

Mini recall (hanya bantuan hafalan, **bukan dasar kesimpulan**):

```
2  = lokal
3  = jaringan
5  = service
10 = RDP
11 = cached
```

## 10. Kelompok Event ID Prioritas

Event ID di bawah ini disusun berdasarkan skenario investigasi, bukan sekadar daftar angka.

### Authentication

- **4624** — successful logon.
- **4625** — failed logon (perlu Audit Logon Events aktif agar tercatat).
- **4634** — account logged off.
- **4647** — user initiated logoff.
- **4648** — logon menggunakan explicit credentials (misalnya RunAs).
- **4672** — special privileges assigned to new logon.
- **4740** — account locked out.

### Account Management

- **4720** — user account created.
- **4722** — user account enabled.
- **4724** — password reset attempt.
- **4725** — user account disabled.
- **4726** — user account deleted.

### Group Management

- **4732** — member added to security-enabled local group.
- **4733** — member removed from security-enabled local group.

**FALSE POSITIVE / KETERBATASAN**
> Group domain dapat menggunakan Event ID yang berbeda dari 4732/4733 (misalnya event untuk grup global/universal). Jangan mengklaim 4732 mencakup seluruh jenis group di semua konteks.

### Process Execution

- **4688** — process creation, **jika** audit process creation aktif. Secara default, **command line tidak ikut tercatat** kecuali kebijakan "Include command line in process creation events" diaktifkan.

### PowerShell

- **4103** — module logging (pipeline execution detail).
- **4104** — script block logging (mencatat isi script block yang diproses PowerShell; lihat Event Card 4104 untuk keterbatasan Base64/obfuscation).

Kedua event ini muncul di channel `Microsoft-Windows-PowerShell/Operational`. Logging penuh melalui Module Logging dan Script Block Logging umumnya memerlukan konfigurasi kebijakan ("Turn on Module Logging" dan "Turn on PowerShell Script Block Logging"); ketersediaan event harus diperiksa berdasarkan versi PowerShell, konfigurasi host, dan evidence.

### Service Persistence

- **4697** — service installed (Security log, bergantung pada audit dan konfigurasi).
- **7045** — service installed (System log, provider Service Control Manager).

Keduanya mencatat instalasi service, tetapi dari channel dan provider yang berbeda — sehingga field yang tersedia juga bisa sedikit berbeda.

### Scheduled Task

- **4698** — scheduled task created.
- **4702** — scheduled task updated.

Channel Task Scheduler Operational dapat memberikan konteks tambahan di luar Security log.

### Defense Evasion dan Log Clearing

- **1102** — Security audit log cleared (Security log).
- **104** — log file cleared pada channel lain (misalnya System), dicatat oleh provider Eventlog.

### Audit Policy

- **4719** — system audit policy changed.

### Defender

Event deteksi dan tindakan Defender berada di channel `Microsoft-Windows-Windows Defender/Operational`. Dua yang paling sering diperiksa adalah **1116** (deteksi) dan **1117** (tindakan), tetapi **wajib** memverifikasi provider, channel, dan field aktual pada evidence — jangan mengasumsikan format selalu sama di semua versi Defender.

### Sysmon

Jika Sysmon tersedia pada evidence:

- **1** — Process Create.
- **3** — Network Connection.
- **11** — File Create.
- **13** — Registry Value Set.

**FALSE POSITIVE / KETERBATASAN**
> Sysmon tidak selalu terpasang. Konfigurasi Sysmon menentukan apa yang dicatat, dan volume event-nya bisa sangat tinggi. Jangan mengandalkan data Sysmon bila evidence yang diberikan tidak menyediakannya.

## 11. Template Pembahasan Setiap Event ID

Bagian ini membahas Event ID prioritas menggunakan format konsisten agar mudah dijadikan referensi cepat.

### Event ID 4624 — An account was successfully logged on

**Makna singkat:**
Sebuah akun berhasil login pada komputer tempat event ini tercatat (bukan tempat akun berasal).

**Log/Provider:**
Security / Microsoft-Windows-Security-Auditing.

**Pertanyaan yang dapat dijawab:**
Siapa yang login, dengan LogonType apa, dari mana, dan kapan?

**Field prioritas:**
- TargetUserName, TargetDomainName, TargetUserSid
- LogonType
- IpAddress, WorkstationName
- LogonId

**Pivot berikutnya:**
- Cari 4634/4647 dengan Logon ID yang sama untuk menemukan waktu logoff.
- Cari 4672 dengan Logon ID yang sama untuk melihat apakah ada privilege khusus.
- Cari aktivitas proses setelah waktu logon ini.

**False positive/keterbatasan:**
4624 sangat umum dan volumenya tinggi — logon berhasil **bukan berarti aman**, dan harus dinilai bersama konteks (waktu, IP, LogonType, akun).

**Contoh interpretasi fiktif:**
"Pada 20:03, akun `svc_backup` login dengan LogonType 10 dari IP 10.10.10.55. Ini indikasi RDP masuk, perlu diverifikasi apakah IP tersebut dikenal sebagai admin workstation."

---

### Event ID 4625 — An account failed to log on

**Makna singkat:**
Percobaan logon gagal.

**Log/Provider:**
Security / Microsoft-Windows-Security-Auditing.

**Pertanyaan yang dapat dijawab:**
Siapa yang mencoba login, dari mana, dan mengapa gagal?

**Field prioritas:**
- TargetUserName
- Failure Reason, Status, Sub Status
- IpAddress
- Caller Process ID
- LogonType

**Pivot berikutnya:**
- Kelompokkan berdasarkan username dan source IP untuk melihat pola.
- Cari 4624 setelahnya dengan user/IP yang sama untuk memastikan apakah percobaan akhirnya berhasil.
- Cari 4740 (lockout) bila kegagalan berulang pada akun yang sama.

**False positive/keterbatasan:**
Event ini **hanya tercatat jika** Audit Logon Events diaktifkan. Sejumlah kecil kegagalan login dapat terjadi karena salah ketik, password lama, service, mapped drive, scheduled task, atau credential yang tersimpan — jangan memakai threshold universal untuk menyatakan brute force. Analisis harus mempertimbangkan volume event, periode waktu, source IP, jumlah target account, pola username, failure reason, successful login setelah failure, account lockout, baseline environment, jenis account, dan jam kejadian.

Brute force: banyak percobaan diarahkan ke satu atau sedikit account. Password spray: satu atau sedikit password dicoba terhadap banyak account. Keduanya tetap harus diverifikasi berdasarkan evidence.

**Contoh interpretasi fiktif:**
"Ditemukan 40 percobaan 4625 dalam 3 menit menuju akun `admin` dari satu IP. Pola ini konsisten dengan brute force, tetapi tetap perlu diverifikasi dengan mencari 4624 berikutnya."

---

### Event ID 4672 — Special privileges assigned to new logon

**Makna singkat:**
Logon baru diberikan sekumpulan privilege sensitif (misalnya privilege administratif).

**Log/Provider:**
Security / Microsoft-Windows-Security-Auditing.

**Pertanyaan yang dapat dijawab:**
Akun mana yang login dengan privilege tinggi, dan session mana yang terkait?

**Field prioritas:**
- SubjectUserName, SubjectUserSid
- Logon ID
- Privileges (daftar privilege yang diberikan)

**Pivot berikutnya:**
- Hubungkan Logon ID dengan 4624 untuk melihat detail logon terkait.
- Periksa apakah Subject adalah security principal yang dikenal (LOCAL SYSTEM, NETWORK SERVICE, LOCAL SERVICE) atau akun administratif yang memang diharapkan memiliki privilege tersebut.

**False positive/keterbatasan:**
**4672 bukan bukti privilege escalation secara otomatis.** Event ini normal terjadi setiap kali akun administratif atau service account login sesuai haknya. Yang perlu dicurigai adalah ketika Subject bukan akun yang diharapkan memiliki privilege tersebut.

**Contoh interpretasi fiktif:**
"Akun `helpdesk01` menerima 4672 pada 20:04, padahal akun ini biasanya tidak memiliki privilege administratif. Perlu diverifikasi apakah ini perubahan group yang sah atau indikasi privilege escalation."

---

### Event ID 4740 — A user account was locked out

**Makna singkat:**
Akun terkunci setelah sejumlah percobaan login gagal.

**Log/Provider:**
Security / Microsoft-Windows-Security-Auditing.

**Pertanyaan yang dapat dijawab:**
Akun mana yang terkunci, dari komputer mana permintaan logon berasal, dan kapan?

**Field prioritas:**
- TargetUserName
- Caller Computer Name

**Pivot berikutnya:**
- Cari kumpulan 4625 sebelumnya menuju akun yang sama untuk memahami pola kegagalan.
- Periksa apakah lockout terjadi karena credential lama tersimpan di suatu aplikasi/service (skenario umum non-malicious), atau karena percobaan brute force aktif.

**False positive/keterbatasan:**
Lockout yang muncul bersamaan dengan lonjakan 4625 adalah indikasi kuat, tetapi tetap bukan bukti tunggal — credential lama yang tersimpan di banyak device juga bisa menyebabkan lockout berulang tanpa niat jahat.

**Contoh interpretasi fiktif:**
"Akun `jsmith` terkunci pada 20:05 setelah 15 kegagalan 4625 dalam 2 menit dari satu source IP. Pola ini mendukung dugaan brute force terarah pada satu akun."

---

### Event ID 4720 / 4732 — Account created & member added to group

**Makna singkat:**
4720: akun user baru dibuat. 4732: sebuah akun ditambahkan sebagai member ke local group tertentu.

**Log/Provider:**
Security / Microsoft-Windows-Security-Auditing.

**Pertanyaan yang dapat dijawab:**
Siapa yang membuat akun/menambahkan member, akun/target apa, ke grup apa, kapan?

**Field prioritas:**
- SubjectUserName, SubjectDomainName, SubjectLogonId (akun/domain/session pelaku perubahan)
- TargetUserName (4720: akun baru) — pada 4732, TargetUserName/TargetDomainName/TargetSid adalah local group tujuan pada raw event
- MemberName, MemberSid (4732) — nama dan SID objek anggota yang ditambahkan
- waktu, host

> **Catatan field 4732:** Pada tampilan Event Viewer, `TargetUserName` dapat ditampilkan dengan label "Group Name". Parser tertentu juga dapat memetakannya menjadi kolom `GroupName`. Namun, nama field parser tidak berlaku universal. Selalu periksa raw XML atau nama kolom aktual.

**Pivot berikutnya:**
- Periksa apakah akun baru ini kemudian login (4624).
- Periksa apakah akun baru menjalankan proses (4688) setelah dibuat.
- Periksa apakah penambahan ke grup diikuti pemberian privilege (4672).

**False positive/keterbatasan:**
Pembuatan akun dan penambahan ke grup administratif adalah aktivitas administrasi rutin di banyak environment. Konteks (siapa Subject, jam berapa, apakah sesuai proses onboarding) menentukan apakah ini normal atau mencurigakan.

**Contoh interpretasi fiktif:**
"Akun `backupsvc` dibuat oleh `Administrator` pada 20:08, lalu ditambahkan ke grup administratif lokal pada 20:10. Perlu diverifikasi apakah ini sesuai proses provisioning service account yang sah."

### Event ID 4688 — A new process has been created

**Makna singkat:**
Sebuah proses baru dijalankan pada sistem.

**Log/Provider:**
Security / Microsoft-Windows-Security-Auditing.

**Pertanyaan yang dapat dijawab:**
Proses apa dijalankan, oleh siapa, dari proses induk apa, dengan command line apa (jika tercatat)?

**Field prioritas:**
- NewProcessName
- ParentProcessName / Creator Process
- SubjectUserName
- ProcessId
- CommandLine (jika audit command-line diaktifkan)

**Pivot berikutnya:**
- Telusuri relasi parent-child process untuk melihat rantai eksekusi.
- Cari 4104 (script block) bila proses adalah PowerShell.
- Cari file/network activity terkait bila tersedia (Sysmon 3/11).

**False positive/keterbatasan:**
Secara default, **command line tidak ikut tercatat**. Tanpa command line, 4688 hanya memberi tahu proses apa yang berjalan, bukan parameter/isinya — ini keterbatasan besar yang harus disebutkan eksplisit dalam laporan bila terjadi.

**Contoh interpretasi fiktif:**
"Proses `powershell.exe` (PID 4521) dijalankan oleh `cmd.exe` (PID 3310) pada 20:06 di bawah konteks user `svc_backup`. Command line tidak tersedia pada evidence ini karena audit command-line tidak aktif."

### Event ID 4104 — PowerShell script block logging

**Makna singkat:**
Mencatat isi script block yang diproses PowerShell ketika Script Block Logging tersedia. Dalam beberapa kasus, isi yang tercatat dapat lebih mudah dibaca dibanding command line awal karena telah melalui parsing atau sebagian normalisasi/deobfuscation — namun ini tidak menjamin seluruh Base64, encrypted string, downloaded content, atau obfuscation otomatis berubah menjadi plaintext; decode dan analisis tambahan tetap dapat diperlukan.

**Log/Provider:**
`Microsoft-Windows-PowerShell/Operational`.

**Pertanyaan yang dapat dijawab:**
Script/command PowerShell apa persis yang dijalankan?

**Field prioritas:**
- ScriptBlockId
- isi script block
- Process ID host PowerShell (untuk dikorelasikan dengan 4688/Sysmon 1)

**Pivot berikutnya:**
- Hubungkan Process ID dengan event process creation untuk melihat parent process dan user.
- Periksa apakah event ini berlevel Warning (indikasi keyword mencurigakan seperti IEX/DownloadString terdeteksi otomatis oleh PowerShell).

**False positive/keterbatasan:**
Event 4104 tidak selalu tersedia; ketersediaannya bergantung pada versi PowerShell dan konfigurasi logging. Script berukuran besar dapat terbagi menjadi beberapa event — `ScriptBlockId` atau nomor bagian dapat diperlukan untuk menggabungkannya. EncodedCommand atau Base64 **bukan otomatis malicious** — banyak tooling administratif sah juga menggunakannya. Isi script harus dinilai bersama user, host, parent process, dan aktivitas lanjutan.

**Contoh interpretasi fiktif:**
"Event 4104 pukul 20:06 mencatat script block yang berisi perintah download file dari URL eksternal. Perlu dikorelasikan dengan proses induk dan user untuk menilai apakah ini aktivitas administratif yang sah atau tidak."

## 12. Authentication Investigation

Workflow umum:

```
FAILED LOGON
  → kelompokkan username
  → kelompokkan source IP
  → periksa waktu
  → cari successful logon
  → cocokkan user, IP, host, dan Logon Type
  → cari privilege/process lanjutan
  → verifikasi
```

### Banyak login gagal

Pertanyaan yang harus dijawab:

- Berapa banyak percobaan?
- Dalam rentang waktu berapa lama?
- Dari IP mana?
- Menuju account apa (satu akun atau banyak akun)?
- Pada host mana?
- Apa Failure Reason-nya?
- Apakah akhirnya diikuti login berhasil?

### Login berhasil setelah gagal

Pola korelasi konseptual:

```
4625 (gagal) → 4624 (berhasil) → 4672 (jika ada privilege) → process/PowerShell → persistence (jika ada)
```

**COMBAT RULE**
> Korelasi ini adalah pola investigasi untuk membangun hipotesis, **bukan bukti otomatis** bahwa keseluruhan rantai adalah satu attack chain. Setiap langkah tetap harus diverifikasi dengan field pendukung (user yang sama, IP yang sama, waktu yang masuk akal).

### Account Lockout

Untuk 4740, periksa: Target account, Caller Computer, waktu, kumpulan event gagal sebelum lockout, dan kemungkinan penyebab non-malicious seperti credential lama yang tersimpan di suatu aplikasi/device.

### RDP

Untuk dugaan aktivitas RDP, periksa: Logon Type 10, IP sumber, username, hostname, serta log Terminal Services sebagai sumber tambahan (dibahas lebih detail di file 03), dan event logoff/disconnect terkait. Jika field IP kosong, catat sebagai keterbatasan evidence, bukan diabaikan begitu saja.

## 13. Account dan Group Modification Investigation

Workflow:

```
TEMUKAN ACCOUNT/GROUP EVENT
  → identifikasi Subject
  → identifikasi Target
  → catat group (jika relevan)
  → catat waktu dan host
  → cari login Subject
  → cari aktivitas Target setelah perubahan
  → verifikasi kebutuhan administratif
```

Skenario yang perlu dibahas dalam investigasi: user baru dibuat, user diaktifkan, password direset, user ditambahkan ke grup administratif, user dihapus.

Pertanyaan penting untuk setiap skenario:

- Siapa pelakunya (Subject)?
- Account apa yang berubah (Target)?
- Group mana yang terlibat?
- Apakah dilakukan pada jam tidak wajar?
- Apakah account baru kemudian login?
- Apakah account baru menjalankan process?
- Apakah perubahan ini sesuai dengan proses administrasi normal yang diketahui?

## 14. Process Execution Investigation

Fokus pada 4688 dan Sysmon Event ID 1 secara konseptual.

Field prioritas: timestamp, user, NewProcessName/Image, ParentProcessName/ParentImage, CommandLine, Process ID, Parent Process ID, integrity/elevation (jika tersedia), host.

Pahami relasi **parent-child process**. Contoh pola fiktif yang layak diperiksa lebih lanjut (bukan otomatis malicious):

```
aplikasi office → script interpreter → PowerShell
```

atau

```
service process → command shell → utility administratif
```

Proses berikut sering muncul dan **sah secara umum**, tetapi juga sering disalahgunakan — nama proses saja **tidak pernah cukup** untuk menyimpulkan sesuatu:

`cmd.exe`, `powershell.exe`, `wscript.exe`, `cscript.exe`, `rundll32.exe`, `regsvr32.exe`, `mshta.exe`, `sc.exe`, `net.exe`, `net1.exe`, `schtasks.exe`.

Yang harus selalu diperiksa bersama nama proses: command line, parent process, user, path eksekusi, waktu, host, dan hasil aktivitas lanjutan.

## 15. PowerShell Investigation

Yang dibahas: process creation PowerShell, command line, script block (4104), module logging (4103), encoded command, indikasi download, execution policy, parent process, user, host.

Workflow:

```
PROSES POWERSHELL DITEMUKAN
  → catat command line
  → cari 4103/4104 terkait
  → decode bila perlu
  → cari network/file/process lanjutan
  → verifikasi konteks
```

**WAJIB PAHAM**

- Base64/encoded command **bukan otomatis malware**.
- EncodedCommand perlu di-decode untuk dibaca isinya (proses decoding dibahas di file 03, bukan di sini).
- Script administrator yang sah juga dapat menghasilkan event 4103/4104.
- Script block logging mungkin tidak aktif pada evidence yang diberikan — catat sebagai keterbatasan.
- Event dapat terpotong atau terbagi menjadi beberapa entri bila script berukuran besar.

## 16. Service Investigation

Workflow:

```
SERVICE EVENT DITEMUKAN
  → catat ServiceName
  → catat ImagePath
  → catat account
  → catat StartType
  → periksa path file
  → cari process terkait
  → periksa waktu pembuatan
  → verifikasi apakah software sah
```

Red flag yang perlu diperiksa lebih lanjut (bukan bukti final):

- executable berada di folder user/temp;
- nama service menyerupai nama service resmi Windows (typosquatting);
- path file tidak biasa;
- ImagePath mengarah ke command shell atau script interpreter;
- service dibuat tidak lama setelah event login yang mencurigakan.

## 17. Scheduled Task Investigation

Field yang diperiksa: TaskName, creator/Subject, action, trigger, command, working directory, user context, waktu pembuatan, event update task, event eksekusi task.

Workflow:

```
TASK CREATED/UPDATED
  → baca TaskName
  → baca XML/action
  → identifikasi executable yang dijalankan
  → cari process execution terkait
  → periksa user context
  → periksa trigger
  → verifikasi apakah ini kebutuhan sah
```

Scheduled task banyak digunakan oleh Windows dan aplikasi resmi untuk update, maintenance, dan automasi — kehadiran task baru bukan otomatis berarti persistence berbahaya.

## 18. Event Log Clearing Investigation

Workflow:

```
LOG CLEARED
  → identifikasi channel yang dibersihkan
  → identifikasi account pelaku
  → catat timestamp
  → cari aktivitas sebelum clearing
  → periksa audit policy
  → periksa kemungkinan maintenance terjadwal
  → cari gap waktu mencurigakan
  → turunkan/naikkan confidence berdasarkan bukti pendukung
```

Kemungkinan penyebab yang harus dipertimbangkan secara adil:

- attacker menghapus jejak (defense evasion);
- administrator melakukan maintenance rutin;
- troubleshooting oleh tim IT;
- policy atau script organisasi yang menjadwalkan pembersihan log.

**FALSE POSITIVE**
> Log clearing adalah indikasi penting yang wajib dicatat, tetapi bukan kesimpulan serangan tanpa konteks pendukung lain.

## 19. Defender Investigation

Cara membaca event Defender secara konseptual: provider/channel, threat name, severity, path, process, user, action, result, remediation, timestamp.

Bedakan dua tahap:

**Detection** — ancaman teridentifikasi oleh engine Defender.

**Action** — Defender mencoba melakukan tindakan terhadap ancaman tersebut.

**Result** — tindakan berhasil, gagal, di-allow, atau memerlukan tindak lanjut manual.

**KESALAHAN UMUM**
> Jangan menyimpulkan bahwa file berbahaya masih aktif hanya karena event deteksi muncul — periksa juga event tindakan/hasil (action/result) yang menyertainya. Sebaliknya, event dengan action "Allow" berarti ancaman terdeteksi tetapi **tidak** diremediasi berdasarkan konfigurasi yang berlaku saat itu.

Korelasikan temuan Defender dengan: process execution terkait, file creation, user yang terlibat, aktivitas network, dan event Defender berikutnya (apakah ada eskalasi atau berhenti di satu event).

## 20. Sysmon Investigation Dasar

Sysmon berfungsi sebagai **telemetry tambahan** di luar Windows Event Log bawaan, dan hanya tersedia jika terpasang serta dikonfigurasi.

Relasi umum antar-event Sysmon:

```
Sysmon 1  Process Create
    ↓
Sysmon 3  Network Connection
    ↓
Sysmon 11 File Create
    ↓
Sysmon 13 Registry Value Set
```

Field umum yang sering dipakai: Image, CommandLine, ParentImage, User, ProcessGuid, ProcessId, DestinationIp, DestinationPort, TargetFilename, TargetObject.

**VERIFIKASI**
> ProcessGuid sangat membantu korelasi antar-event Sysmon karena nilainya unik per proses dan lebih stabil untuk pivot dibanding ProcessId saja (yang bisa dipakai ulang oleh OS dari waktu ke waktu).

## 21. Raw Event, CSV, dan SIEM Field Mapping

Tabel berikut adalah **contoh mapping umum**, bukan mapping universal — nama field aktual dapat berbeda tergantung parser dan SIEM yang digunakan.

| Konsep | Raw Windows Event | CSV Parser | SIEM |
|---|---|---|---|
| Waktu | TimeCreated/SystemTime | TimeCreated | @timestamp atau field waktu sejenis |
| Event ID | EventID | EventId | event.code atau field sejenis |
| Host | Computer | Computer | host.name |
| User | Target/Subject fields | kolom hasil parser | user.name atau field sejenis |
| IP | IpAddress | IpAddress/Payload | source.ip |
| Process | NewProcessName | ProcessName/Payload | process.executable |
| Command | CommandLine | CommandLine/Payload | process.command_line |

Poin penting:

- SIEM berbeda dapat menggunakan schema field yang berbeda pula.
- Parser tertentu dapat memakai nama kolom yang tidak sama persis dengan nama field raw XML.
- Selalu periksa field **aktual** pada evidence yang diberikan sebelum mengasumsikan nama kolom.
- Jangan menyalin query dari satu engine SIEM ke engine lain tanpa adaptasi nama field.

## 22. Query Logic Engine-Neutral

Bagian ini mengajarkan **pola berpikir query**, bukan syntax khusus satu tool.

Pola 1 — pencarian spesifik:

```
event ID = X
AND user = Y
AND timestamp within range
```

Pola 2 — agregasi:

```
failed authentication
GROUP BY source IP, username
COUNT
SORT descending
```

Pola 3 — pencarian berbasis konten:

```
process name contains PowerShell
AND command line exists
AND user not expected
```

Operator konsep yang perlu dipahami: equals, contains, starts with, exists, AND, OR, NOT, range, grouping, count, sort.

Contoh pseudo-query dan artinya:

| Pseudo-query | Arti |
|---|---|
| `EventID = 4625 GROUP BY IpAddress COUNT` | Menghitung jumlah percobaan gagal per IP sumber |
| `EventID = 4688 AND ParentProcessName contains "winword"` | Mencari proses yang dilahirkan dari Microsoft Word |
| `EventID = 4732 AND TargetUserName contains "Admin"` | Mencari penambahan member ke grup administratif (sebagian parser menamai field ini `GroupName`; verifikasi nama kolom aktual) |

Tutorial syntax khusus (KQL, Lucene, SPL, Wazuh) **tidak dibahas di file ini** — akan dipraktikkan di file 03.

## 23. Timeline dan Correlation Berbasis Event

Contoh fiktif (bukan incident nyata):

```
20:00 — failed login
20:01 — failed login
20:03 — successful login
20:04 — special privileges
20:06 — PowerShell process
20:08 — account created
20:10 — member added to group
20:13 — service installed
20:17 — log cleared
```

| Waktu | Event | User | Host | IP | Correlation Key | Temuan | Klasifikasi | Confidence |
|---|---|---|---|---|---|---|---|---|
| 20:00–20:01 | 4625 | admin | HOST01 | 10.10.10.55 | belum tersedia | Percobaan login gagal berulang tercatat | INDIKASI | MEDIUM |
| 20:03 | 4624 | admin | HOST01 | 10.10.10.55 | Logon ID `0x3E7` (Contoh fiktif) | Login berhasil setelah beberapa kegagalan | FAKTA | HIGH |
| 20:04 | 4672 | admin | HOST01 | — | Logon ID `0x3E7` (Contoh fiktif) | Privilege administratif diberikan pada logon dengan Logon ID yang sama seperti 4624 di atas | FAKTA | HIGH |
| 20:06 | 4104 | admin | HOST01 | — | belum tersedia | PowerShell tercatat pada user dan host yang sama serta berdekatan waktu. Hubungan session belum terverifikasi | INDIKASI | LOW |
| 20:08 | 4720 | admin | HOST01 | — | belum tersedia | Akun dibuat oleh user yang sama pada host yang sama. Periksa SubjectLogonId sebelum menyatakan aktivitas berasal dari session login yang sama | INDIKASI | LOW |
| 20:10 | 4732 | admin | HOST01 | — | belum tersedia | Akun ditambahkan ke local group | FAKTA | HIGH |
| 20:10 | 4732 | admin | HOST01 | — | belum tersedia | Penambahan tersebut mungkin digunakan untuk privilege escalation | DUGAAN | LOW atau MEDIUM, bergantung korelasi |
| 20:13 | 7045 | SYSTEM | HOST01 | — | belum tersedia | Service baru tercatat sebagai diinstal | FAKTA | HIGH |
| 20:13 | 7045 | SYSTEM | HOST01 | — | belum tersedia | Service tersebut mungkin digunakan sebagai persistence | DUGAAN | LOW |
| 20:17 | 1102 | admin | HOST01 | — | belum tersedia | Security audit log tercatat telah dibersihkan | FAKTA | HIGH |
| 20:17 | 1102 | admin | HOST01 | — | belum tersedia | Log mungkin dibersihkan untuk menghapus jejak | DUGAAN | LOW atau MEDIUM, bergantung event pendukung |

Catatan penting:

- Timeline harus dibangun dari timestamp yang **sudah disamakan timezone**-nya (lihat file 01).
- Keberadaan event adalah FAKTA; makna serangan adalah INDIKASI atau DUGAAN sampai diverifikasi lebih lanjut.
- Klasifikasi dan Confidence adalah dua hal berbeda: Klasifikasi menunjukkan jenis pernyataan (FAKTA/INDIKASI/DUGAAN/KESIMPULAN), Confidence menunjukkan kekuatan evidence yang mendukung interpretasi (LOW/MEDIUM/HIGH).
- **SAME USER + SAME HOST + CLOSE TIME tidak otomatis berarti SAME SESSION.** Klaim "session yang sama" hanya boleh dinyatakan bila ada correlation key yang mendukung (Logon ID, SubjectLogonId, Process ID, Parent Process ID, ProcessGuid, ScriptBlockId). Jika belum tersedia, tulis "belum tersedia" dan turunkan confidence.
- Hubungan berdasarkan urutan waktu saja **belum cukup** untuk kesimpulan akhir.
- Tetap verifikasi user, host, IP, Logon ID, process, dan konteks lain sebelum menaikkan level confidence menjadi kesimpulan.
- Nilai Logon ID pada tabel di atas adalah **contoh fiktif** dan tidak boleh diperlakukan sebagai nilai dari evidence nyata.
- Contoh ini **fiktif** dan tidak boleh diperlakukan sebagai incident nyata.

## 24. Playbook Skenario Prioritas

Setiap playbook menggunakan format: OBJECTIVE, PRIMARY EVENT, FIELDS, PIVOT, VERIFY, FALSE POSITIVE, OUTPUT.

### Playbook A — Brute Force atau Password Spray

```
OBJECTIVE       : Menentukan apakah terjadi percobaan brute force/password spray
PRIMARY EVENT   : 4625
FIELDS          : TargetUserName, IpAddress, Failure Reason, waktu
PIVOT           : 4624 (berhasil), 4672 (privilege), 4740 (lockout)
VERIFY          : pola satu IP → banyak user, atau satu user → banyak percobaan
FALSE POSITIVE  : service account salah konfigurasi, aplikasi dengan credential lama
OUTPUT          : daftar IP/akun terdampak beserta timeline percobaan
```

### Playbook B — Akun Baru Mencurigakan

```
OBJECTIVE       : Menilai apakah akun baru merupakan backdoor account
PRIMARY EVENT   : 4720
FIELDS          : Subject, Target, waktu, host
PIVOT           : 4722 (enable), 4732 (group), 4624 (login), 4688 (process)
VERIFY          : kesesuaian dengan proses onboarding/administrasi normal
FALSE POSITIVE  : provisioning akun baru yang sah oleh tim IT
OUTPUT          : profil akun baru beserta aktivitas setelah pembuatan
```

### Playbook C — Penambahan ke Grup Administratif

```
OBJECTIVE       : Menilai apakah penambahan member ke grup administratif wajar
PRIMARY EVENT   : 4732
FIELDS          : SubjectUserName (actor), MemberName/MemberSid (anggota), TargetUserName/TargetDomainName (grup tujuan, kadang ditampilkan sebagai "Group Name"/`GroupName` oleh parser), host, waktu
PIVOT           : login actor, login member, process, 4720 (jika member baru dibuat)
VERIFY          : apakah actor berwenang melakukan perubahan tersebut
FALSE POSITIVE  : perubahan group rutin oleh admin yang berwenang
OUTPUT          : catatan actor, member, group, dan waktu perubahan
```

### Playbook D — PowerShell Mencurigakan

```
OBJECTIVE       : Menilai apakah eksekusi PowerShell berbahaya
PRIMARY EVENT   : 4688 (proses) dan 4104 (script block)
FIELDS          : CommandLine/isi script, ParentProcess, user
PIVOT           : 4103, network/file activity lanjutan, Defender
VERIFY          : isi script, konteks user, parent process
FALSE POSITIVE  : script administrasi/automasi yang sah
OUTPUT          : ringkasan isi script beserta rantai proses terkait
```

### Playbook E — Service Persistence

```
OBJECTIVE       : Menilai apakah service baru merupakan mekanisme persistence
PRIMARY EVENT   : 7045 (dan 4697 jika tersedia)
FIELDS          : ServiceName, ImagePath, account, StartType
PIVOT           : proses eksekusi file terkait, user, login sebelumnya
VERIFY          : path file, kewajaran nama service, waktu pembuatan
FALSE POSITIVE  : instalasi software resmi
OUTPUT          : detail service beserta status verifikasi
```

### Playbook F — Scheduled Task

```
OBJECTIVE       : Menilai apakah scheduled task baru merupakan persistence
PRIMARY EVENT   : 4698
FIELDS          : TaskName, action, creator, trigger
PIVOT           : eksekusi task terkait, file path, user, event update (4702)
VERIFY          : kewajaran action/trigger dibanding fungsi task
FALSE POSITIVE  : task bawaan Windows/aplikasi resmi
OUTPUT          : detail task beserta status verifikasi
```

### Playbook G — Event Log Cleared

```
OBJECTIVE       : Menilai apakah log clearing merupakan defense evasion
PRIMARY EVENT   : 1102 (dan 104 pada channel lain jika ada)
FIELDS          : channel, account, timestamp, host
PIVOT           : event sebelum clearing, audit policy, login, process
VERIFY          : konteks maintenance yang diketahui
FALSE POSITIVE  : maintenance terjadwal, troubleshooting IT
OUTPUT          : catatan waktu clearing, akun pelaku, dan aktivitas sebelumnya
```

## 25. Keterbatasan Windows Event Log

- Audit policy dapat tidak aktif untuk kategori tertentu.
- Log dapat overwrite (event lama tertimpa event baru) jika ukuran log terbatas.
- Retention dapat terbatas tergantung konfigurasi.
- Event dapat hilang karena berbagai alasan teknis.
- Beberapa field dapat kosong meski event-nya tercatat.
- IP dapat tidak tersedia pada beberapa jenis logon.
- Command line dapat tidak dicatat bila audit khusus tidak aktif.
- Sysmon dapat tidak terpasang sama sekali.
- PowerShell logging dapat tidak lengkap jika hanya sebagian fitur diaktifkan.
- Timestamp dapat tampil berbeda tergantung tool dan timezone display.
- SIEM dapat melakukan normalisasi yang mengubah representasi field asli.
- Ketiadaan sebuah event **bukan bukti** bahwa aktivitas tersebut tidak terjadi.

**COMBAT RULE**
> Tuliskan "tidak ditemukan pada evidence dan rentang yang diperiksa", bukan "tidak pernah terjadi". Perbedaan bahasa ini penting untuk keakuratan laporan investigasi.

## 26. False Positive dan Interpretasi Aman

| Aktivitas | Bisa mencurigakan karena | Bisa normal karena | Verifikasi |
|---|---|---|---|
| Banyak login gagal | brute force | password lama tersimpan/service | IP, user, pola waktu |
| PowerShell dengan encoded command | script attacker | administrasi/automasi | isi command, parent process |
| Service baru | persistence | instalasi software | path, kewajaran nama |
| Scheduled task baru | persistence | updater aplikasi | action, creator |
| Account baru | backdoor account | onboarding karyawan | creator, waktu, proses |
| Log cleared | defense evasion | maintenance terjadwal | akun, konteks, waktu |
| Event privilege (4672) | escalation | login admin normal | session, process terkait |

## 27. Kesalahan Umum Pemula

| Kesalahan | Mengapa salah | Cara memperbaiki |
|---|---|---|
| Menghafal Event ID tanpa memahami field | Tidak bisa menjawab pertanyaan investigasi sebenarnya | Fokus pada field dan konteks, bukan hafalan angka |
| Menganggap 4624 selalu aman | Login berhasil bisa jadi login attacker dengan credential valid | Periksa LogonType, IP, waktu, dan konteks |
| Menganggap 4625 selalu brute force | Kegagalan sesekali adalah hal wajar | Periksa volume, pola, dan sumbernya |
| Menganggap 4672 selalu privilege escalation | Event ini normal untuk login admin/service yang sah | Periksa apakah Subject memang berhak atas privilege tersebut |
| Menganggap Logon Type 3 adalah RDP | Type 3 adalah Network, bukan RemoteInteractive | Ingat Type 10 untuk RDP, bukan Type 3 |
| Menganggap Logon Type 10 selalu serangan | RDP legitimate juga memakai Type 10 | Periksa IP, user, dan waktu |
| Menganggap PowerShell selalu malware | PowerShell adalah tool administrasi resmi | Periksa isi script dan konteksnya |
| Menganggap service baru selalu persistence | Banyak software resmi menginstal service | Periksa path, nama, dan waktu instalasi |
| Menganggap log clearing otomatis membuktikan attacker | Bisa jadi maintenance terjadwal | Cari konteks pendukung sebelum menyimpulkan |
| Mengabaikan provider | Event ID sama bisa berarti berbeda di provider berbeda | Selalu catat provider bersama Event ID |
| Mengabaikan channel | Channel menentukan konteks dan asal event | Catat channel di setiap temuan |
| Tidak melihat raw event | Parser bisa menyembunyikan atau mengganti nama field | Verifikasi ke raw XML bila ragu |
| Salah Subject dan Target | Kesimpulan pelaku/korban jadi terbalik | Selalu cocokkan nama field secara eksplisit |
| Tidak memeriksa timezone | Timeline jadi tidak akurat | Samakan timezone sebelum menyusun timeline |
| Tidak mencari event pendukung | Kesimpulan dibangun dari satu event saja | Selalu cari event pivot lanjutan |
| Mengandalkan Sysmon padahal tidak tersedia | Analisis jadi berdasarkan asumsi, bukan evidence | Cek dulu apakah Sysmon ada di evidence |

## 28. Mini Practice Konseptual

17. Apa perbedaan klasifikasi dan confidence?

### Cek Jawaban Konseptual

1. Security umumnya berisi authentication, account/group management, privilege, dan (jika audit aktif) process creation serta log clearing; System umumnya berisi service, driver, boot/shutdown, dan error sistem — keduanya melengkapi satu sama lain, bukan saling menggantikan.
2. Event ID yang sama dapat dipakai ulang oleh provider berbeda dengan arti berbeda; mengabaikan provider berisiko salah menginterpretasikan jenis aktivitas yang sebenarnya terjadi.
3. Subject adalah Administrator (pelaku), Target adalah `finance01` (akun yang terkena tindakan).
4. Tidak. Logon Type 3 (Network) juga terjadi pada aktivitas normal seperti mengakses file share; harus dinilai bersama IP, user, dan waktu.
5. Tidak. RDP yang sah juga menghasilkan Logon Type 10; perlu diperiksa apakah IP dan user sesuai dengan pola yang diharapkan.
6. Cocokkan Logon ID pada 4624 dengan event-event berikutnya (4672, process creation) untuk melihat apa yang dilakukan setelah login berhasil.
7. Karena 4672 juga tercatat secara normal setiap kali akun administratif atau service account login sesuai haknya; yang perlu dicurigai adalah ketika Subject-nya tidak seharusnya memiliki privilege tersebut.
8. Subject (pelaku pembuatan), TargetUserName (akun baru), waktu, dan host tempat event tercatat.
9. Subject adalah pelaku yang melakukan penambahan; Member adalah akun yang ditambahkan sebagai anggota grup — keduanya bisa jadi akun yang berbeda.
10. Karena nama proses saja tidak menunjukkan isi/parameter perintah; 4104 mencatat isi script block yang diproses PowerShell, yang terkadang lebih mudah dibaca berkat parsing/normalisasi sebagian, sehingga umumnya memberi konteks yang lebih lengkap — meski isi yang tercatat tidak selalu sepenuhnya plaintext dan tetap dapat memerlukan decode/analisis tambahan.
11. ServiceName (untuk mengidentifikasi service apa yang diinstal) dan ImagePath (untuk mengetahui file executable apa yang dijalankan service tersebut, termasuk apakah lokasinya wajar).
12. Karena log clearing juga bisa berasal dari maintenance rutin atau troubleshooting IT yang sah; harus dicari konteks pendukung (akun pelaku, waktu, aktivitas sebelumnya) sebelum menyimpulkan sebagai serangan.
13. Parser CSV bisa mengganti nama field atau memindahkan sebagian data ke kolom generik, sehingga detail penting bisa terlewat atau salah dibaca tanpa verifikasi ke raw event.
14. Contoh: field IP pada raw event bernama `IpAddress`, pada CSV bisa jadi `IpAddress` atau masuk ke kolom `Payload`, dan pada SIEM sering dinamai `source.ip`; jika diabaikan, analis bisa gagal menemukan field yang dicari karena mengira datanya tidak ada.
15. Karena urutan waktu saja tidak membuktikan hubungan sebab-akibat; event-event yang berdekatan waktu bisa jadi tidak saling terkait, sehingga tetap perlu verifikasi user, host, IP, Logon ID, dan proses sebelum menaikkan level confidence.
16. Belum. Perlu correlation key seperti Logon ID, SubjectLogonId, ProcessGuid, Process ID, ScriptBlockId, atau evidence session lain.
17. Klasifikasi menunjukkan jenis pernyataan (FAKTA/INDIKASI/DUGAAN/KESIMPULAN), sedangkan confidence menunjukkan kekuatan evidence yang mendukung interpretasi (LOW/MEDIUM/HIGH).
