## 3. Mental Model Utama Investigasi

  

Seluruh proses investigasi pada H1 mengikuti satu alur yang sama:

  

```

QUESTION → EVIDENCE → FILTER → PIVOT → CORRELATE → VERIFY → ANSWER → DOCUMENT

```

  

Alur ini bukan langkah kaku satu arah. Pengguna bisa kembali ke tahap sebelumnya kapan saja — misalnya dari VERIFY kembali ke FILTER karena hasil awal ternyata kurang tepat.

  

### QUESTION

  

- Apa yang sebenarnya ditanyakan oleh soal?

- Apa format jawaban yang diminta — nama user, IP, hostname, timestamp, atau urutan aktivitas?

- Apakah jawaban berupa satu nilai tunggal, atau beberapa nilai (misalnya daftar host)?

  

### EVIDENCE

  

- Evidence apa saja yang tersedia untuk soal ini?

- Apakah berbentuk log mentah, CSV hasil parsing, dashboard SIEM, screenshot, atau berkas lain?

- Evidence mana yang paling relevan dengan objective?

- Apakah evidence yang tersedia sudah cukup untuk menjawab, atau perlu evidence tambahan?

  

### FILTER

  

Memperkecil volume data berdasarkan waktu, Event ID, user, host, IP, process, atau kata kunci, sehingga data yang dilihat menjadi relevan dan mudah dibaca.

  

### PIVOT

  

Bergerak dari satu temuan menuju field lain yang berkaitan. Contoh alur: user → IP → host → process → event berikutnya.

  

### CORRELATE

  

Menghubungkan beberapa event yang memiliki kesamaan waktu, user, host, IP, process, session, atau konteks, sehingga membentuk gambaran yang lebih utuh dibanding satu event saja.

  

### VERIFY

  

Memastikan hasil bukan salah baca, noise, atau false positive, dengan memeriksa raw event atau sumber kedua sebelum dipakai sebagai jawaban.

  

### ANSWER

  

Menjawab hanya apa yang diminta, mengikuti format flag atau format jawaban yang ditentukan soal — tanpa menambahkan detail yang tidak diminta.

  

### DOCUMENT

  

Menyimpan screenshot, menulis findings, mencatat query/filter/timestamp yang dipakai, dan memperbarui write-up sebelum berpindah ke soal berikutnya.

  

**Contoh mini (fiktif, bukan evidence latihan final):**

  

Soal fiktif menanyakan "user mana yang berhasil login setelah beberapa kali gagal login pada malam hari?"

  

1. QUESTION — jawaban berupa satu username.

2. EVIDENCE — log otentikasi tersedia dalam bentuk CSV hasil parsing.

3. FILTER — persempit ke rentang waktu malam hari dan event terkait login.

4. PIVOT — dari event gagal login, pindah ke field username dan source IP yang sama.

5. CORRELATE — hubungkan beberapa percobaan gagal dengan satu percobaan berhasil pada user dan IP yang sama.

6. VERIFY — buka raw event dari percobaan berhasil untuk memastikan username dan waktunya benar.

7. ANSWER — tuliskan username sesuai format yang diminta.

8. DOCUMENT — simpan screenshot event berhasil login beserta catatan filter yang dipakai.

  

> **WAJIB PAHAM**

> Kedelapan tahap ini adalah kerangka berpikir default. Semakin sering dipakai, semakin cepat pengguna bergerak dari soal ke soal tanpa kehilangan arah.

## 4. Memecah Objective dengan WHO–WHAT–WHEN–WHERE–HOW–PROOF

  

Sebelum membuka tool apa pun, objective soal perlu dipecah menjadi enam unsur berikut.

  

### WHO

  

Siapa yang terlibat — user, account, service account, atau pemilik host/process.

  

### WHAT

  

Aktivitas yang terjadi, misalnya: login, login gagal, pembuatan user, perubahan group, eksekusi process, pembuatan service, pembuatan scheduled task, atau pembersihan log. (Daftar ini hanya contoh kategori, bukan daftar Event ID lengkap.)

  

### WHEN

  

Timestamp, rentang waktu, urutan kejadian, dan timezone yang berlaku.

  

### WHERE

  

Hostname, source IP, workstation, destination, atau log source tempat aktivitas tercatat.

  

### HOW

  

Process, command line, service, scheduled task, metode logon, atau tool yang dipakai untuk melakukan aktivitas tersebut.

  

### PROOF

  

Event, field, raw data, screenshot, dan evidence pendukung yang membuktikan jawaban.

  

**Template:**

  

```

Objective:

WHO     :

WHAT    :

WHEN    :

WHERE   :

HOW     :

PROOF   :

Format jawaban:

```

  

**Tiga contoh objective fiktif (bukan dari Guided Lab):**

  

1. *"Tentukan user yang membuat akun baru pada dini hari dan host tempat aktivitas tersebut terjadi."*

   WHO: user pembuat akun. WHAT: pembuatan akun baru. WHEN: dini hari (perlu dipersempit dari rentang waktu soal). WHERE: hostname tempat aktivitas tercatat. HOW: metode/tool yang dipakai untuk membuat akun. PROOF: event pembuatan akun beserta field aktor dan target.

  

2. *"Identifikasi proses yang dijalankan tidak lama setelah sebuah login mencurigakan."*

   WHO: user yang login. WHAT: login diikuti eksekusi process. WHEN: rentang waktu singkat setelah login. WHERE: host tempat login dan proses berjalan. HOW: command line atau parent process yang menjalankannya. PROOF: event login dan event eksekusi process yang berdekatan waktu.

  

3. *"Tentukan kapan sebuah service baru muncul di salah satu host dan siapa yang membuatnya."*

   WHO: akun pembuat service. WHAT: pembuatan service baru. WHEN: timestamp pembuatan. WHERE: hostname tempat service dibuat. HOW: image path atau cara service dijalankan. PROOF: event pembuatan service dengan field terkait.

## 5. Mengenali Jenis Evidence

  

| Jenis | Fungsi | Kelebihan | Keterbatasan |

|---|---|---|---|

| EVTX | Sumber log asli Windows | Detail lengkap, dapat diverifikasi | Volume besar, kurang praktis untuk pencarian cepat |

| CSV | Hasil parsing evidence | Mudah difilter, disortir, dan dicari | Bukan pengganti mutlak EVTX asli, tergantung akurasi parser |

| SIEM | Memusatkan dan mengindeks event | Mudah untuk query, agregasi, dan pivot | Nama field dapat berubah karena normalisasi |

| Screenshot | Bukti visual temuan | Cepat dipahami, mudah dilampirkan | Tidak boleh menggantikan catatan findings |

| Text export | Salinan data mentah dalam teks | Mudah dicari dengan keyword | Tidak selalu terstruktur |

| Findings | Catatan hasil investigasi | Menghubungkan evidence dengan kesimpulan | Perlu konsistensi format agar mudah ditelusuri |

| Write-up | Dokumentasi kronologis proses | Menjelaskan alur pengerjaan secara utuh | Percuma jika ditulis di akhir tanpa catatan berjalan |

  

**EVTX** adalah sumber log asli yang dapat dibuka di Event Viewer, digunakan terutama untuk verifikasi detail.

  

**CSV** adalah hasil parsing yang mempermudah pencarian, filtering, dan sort, tetapi bukan pengganti mutlak EVTX asli.

  

**SIEM** memusatkan dan mengindeks event sehingga mempermudah query, agregasi, dan pivot; namun nama field bisa berbeda dari nama field aslinya karena proses normalisasi.

  

**Screenshot** adalah bukti visual yang harus menampilkan konteks cukup, dan tidak boleh menjadi satu-satunya bentuk dokumentasi.

  

**Findings** adalah catatan yang menghubungkan evidence dengan kesimpulan investigasi.

  

**Write-up** adalah dokumentasi kronologis dari proses dan hasil investigasi secara keseluruhan.

## 6. Evidence Handling

  

Gunakan workflow berikut untuk setiap evidence yang diterima:

  

```

INBOX

  → salin ke ORIGINAL

    → hitung SHA-256 ORIGINAL

      → salin ke WORKING

        → verifikasi salinan

          → analisis WORKING

            → simpan hasil ke OUTPUT

```

  

- **INBOX** — file yang baru diterima atau diunduh, belum diproses.

- **ORIGINAL** — salinan evidence yang dipertahankan tanpa perubahan sama sekali.

- **WORKING** — salinan yang dipakai untuk parsing dan analisis sehari-hari.

- **OUTPUT** — CSV, screenshot, findings, timeline, dan write-up yang dihasilkan dari analisis.

  

> **COMBAT RULE**

> Jangan melakukan parsing atau perubahan langsung pada ORIGINAL.

  

Beberapa catatan penting:

  

- Membuka EVTX secara read-only untuk verifikasi tetap harus dilakukan dengan hati-hati agar tidak tertukar dengan file yang sedang diproses.

- ORIGINAL tidak boleh ditimpa dalam kondisi apa pun.

- Output parser (CSV, hasil ekspor, dan lain-lain) tidak disimpan di folder ORIGINAL.

- Nama file asli harus dicatat.

- Sumber file harus dicatat.

- Timezone yang berlaku saat file diterima harus dicatat.

- Setiap turunan evidence (hasil parsing, hasil konversi) harus dibedakan secara jelas dari file aslinya, misalnya lewat penamaan folder ORIGINAL vs WORKING.

## 7. Integritas Evidence dan Hash

  

Hash adalah "sidik jari digital" sebuah file. SHA-256 dipakai untuk memeriksa apakah isi file berubah:

  

- Hash yang sama menunjukkan isi file identik dengan probabilitas yang sangat tinggi.

- Hash yang berbeda menunjukkan ada perbedaan isi, sekecil apa pun.

  

Alur pemakaian hash dalam evidence handling:

  

```

ORIGINAL hash

  → salin ke WORKING

    → WORKING hash

      → bandingkan

```

  

Jika salinan identik, maka:

  

```

ORIGINAL SHA-256 = WORKING SHA-256

```

  

Jika file diekstrak, dikonversi, atau diparse menjadi format lain (misalnya EVTX → CSV), hash hasil turunan **wajar berbeda** — ini bukan tanda kerusakan, karena isi berkasnya memang berubah bentuk.

  

**Praktik: Menghitung hash SHA-256 sebuah file**

  

| Bagian | Isi |

|---|---|

| TUJUAN | Memastikan salinan WORKING identik dengan ORIGINAL sebelum dianalisis |

| INPUT | Path file evidence yang akan dihitung hash-nya |

| LANGKAH | Jalankan perintah hash pada ORIGINAL, lalu pada WORKING |

| HASIL YANG DIHARAPKAN | Nilai SHA-256 dari kedua file |

| VERIFIKASI | Bandingkan kedua nilai SHA-256 secara langsung, karakter demi karakter |

| INTERPRETASI | Sama berarti salinan identik; berbeda berarti ada perubahan yang harus ditelusuri |

| KESALAHAN UMUM | Menghitung hash pada file yang salah, atau lupa mencatat hasilnya |

| OUTPUT | Catatan hash pada working notes atau tabel evidence |

  

Contoh perintah PowerShell:

  

```powershell

Get-FileHash "PATH_FILE" -Algorithm SHA256

```

  

Contoh pemanggilan dari CMD:

  

```cmd

powershell -Command "Get-FileHash 'PATH_FILE' -Algorithm SHA256"

```

  

Perintah ini menghitung nilai hash SHA-256 dari file pada `PATH_FILE`, sehingga hasilnya dapat dibandingkan antara ORIGINAL dan WORKING tanpa perlu membuka isi file satu per satu.

  

Format pencatatan hash:

  

```

Evidence          :

Path ORIGINAL     :

Path WORKING      :

SHA-256 ORIGINAL  :

SHA-256 WORKING   :

Status            :

Tanggal           :

Sumber            :

```

  

> **WAJIB PAHAM**

> Jangan pernah mengarang nilai hash. Jika hash belum sempat dihitung, tulis "belum dihitung", bukan nilai palsu.

	## 8. Chain of Custody Sederhana untuk Kompetisi
	
	  
	
	Lomba tidak selalu memerlukan formulir hukum lengkap seperti pada investigasi forensik resmi, tetapi pengguna tetap perlu mencatat:
	
	  
	
	- Nama evidence.
	
	- Sumber evidence.
	
	- Waktu diterima.
	
	- Lokasi penyimpanan.
	
	- Hash file.
	
	- Salinan yang dibuat.
	
	- Tool yang digunakan.
	
	- Output yang dihasilkan.
	
	- Perubahan yang dilakukan (jika ada).
	
	  
	
	Tabel pencatatan sederhana:
	
	  
	
	| Waktu | Aktivitas | File | Tool | Output | Catatan |
	
	|---|---|---|---|---|---|
	
	| | | | | | |
	
	  
	
	Manfaat pencatatan ini:
	
	  
	
	- Mengurangi kebingungan saat evidence bertambah banyak.
	
	- Memudahkan penyusunan write-up di akhir.
	
	- Mencegah salah file saat berpindah antar soal.
	
	- Memudahkan mengulang langkah bila hasil perlu diverifikasi ulang.
	
	  
	
	Istilah yang dipakai pada file ini adalah **"chain of custody sederhana untuk kompetisi"**, bukan prosedur hukum penuh.

	## 9. Timestamp dan Timezone
	
	  
	
	Bagian ini penting karena kesalahan timezone adalah salah satu penyebab jawaban salah yang paling sering terjadi.
	
	  
	
	Beberapa hal dasar:
	
	  
	
	- Timestamp adalah waktu yang tercatat pada sebuah event.
	
	- Timestamp dapat ditampilkan sebagai local time atau UTC, tergantung tool.
	
	- SIEM, EVTX, CSV, dan sistem operasi dapat menampilkan zona waktu yang berbeda satu sama lain.
	
	- Urutan kejadian bisa terlihat salah kalau timezone tidak diperiksa terlebih dahulu.
	
	- Waktu file dibuat, waktu file dimodifikasi, waktu event dicatat, dan waktu log diterima bisa berbeda-beda.
	
	  
	
	Konsep dasar:
	
	  
	
	- **UTC** — waktu universal sebagai acuan.
	
	- **Local time** — waktu sesuai zona lokal perangkat atau tool.
	
	- **Offset** — selisih antara local time dan UTC.
	
	- **Asia/Jakarta** — zona waktu WIB.
	
	- **WIB = UTC+7**
	
	  
	
	Contoh konversi:
	
	  
	
	```
	
	10:00 UTC → 17:00 WIB
	
	```
	
	  
	
	Langkah sebelum menjawab pertanyaan berbasis waktu:
	
	  
	
	1. Catat timezone perangkat yang dipakai.
	
	2. Catat timezone yang dipakai tool (Event Viewer, parser, SIEM).
	
	3. Periksa format timestamp yang ditampilkan.
	
	4. Periksa apakah soal meminta jawaban dalam UTC atau local time.
	
	5. Konversi hanya jika benar-benar diperlukan.
	
	6. Tulis timezone yang dipakai pada catatan findings.
	
	  
	
> 	**COMBAT RULE**
	
> 	Jangan menjawab timestamp sebelum memastikan timezone.
	
	  
	
	Kesalahan umum terkait waktu:
	
	  
	
	- Menganggap semua timestamp yang terlihat sudah dalam WIB.
	
	- Mengurutkan event dari sumber dengan format waktu yang berbeda tanpa menyamakan dulu.
	
	- Mengubah waktu tanpa mencatat offset yang dipakai.
	
	- Menghilangkan detik yang justru penting untuk urutan kejadian.
	
	- Menggunakan waktu screenshot diambil sebagai waktu event terjadi.

	## 10. Sorting dan Time Range
	
	  
	
	- Sort **ascending** membantu melihat urutan dari awal ke akhir.
	
	- Sort **descending** membantu mencari kejadian terbaru lebih cepat.
	
	- Time range yang tepat mengurangi noise pada data.
	
	- Time range yang terlalu sempit dapat menghilangkan evidence penting.
	
	- Time range yang terlalu lebar dapat membuat analisis menjadi lambat dan membingungkan.
	
	  
	
	Strategi penggunaan time range:
	
	  
	
	1. Mulai dari rentang waktu yang diberikan pada soal.
	
	2. Tambahkan buffer waktu sebelum dan sesudah rentang tersebut.
	
	3. Temukan event utama di dalam rentang itu.
	
	4. Perluas rentang bila diperlukan untuk melihat konteks sekitar.
	
	5. Persempit kembali saat sudah siap mengambil screenshot.
	
	  
	
	**Contoh fiktif:** Objective menyebut insiden terjadi sekitar pukul 20:00. Mulai dari rentang 19:45–20:15. Jika ditemukan event penting pada 19:44, perluas rentang ke 19:30 agar konteks sebelumnya ikut terlihat.

## 11. Filtering

  

Filtering adalah proses memperkecil volume data agar lebih mudah dianalisis. Filter dapat dibuat berdasarkan: waktu, Event ID, user, host, IP, process, channel, provider, keyword, atau command line.

  

Prinsip dasar:

  

```

Mulai luas → temukan pola → sempitkan → verifikasi

```

  

Kesalahan umum saat filtering:

  

- Memakai terlalu banyak filter sekaligus sejak awal.

- Salah menuliskan nama field.

- Salah format nilai yang dicari.

- Lupa menyesuaikan time range.

- Menganggap "no result" berarti aktivitas tidak pernah terjadi.

  

**Emergency flow saat filter tidak menghasilkan apa-apa:**

  

```

NO RESULT

  → cek time range

    → cek timezone

      → hapus filter tambahan

        → cari dengan keyword yang lebih kasar

          → buka raw event

            → cek nama field yang sebenarnya dipakai

              → cek log source

```

## 12. Pivoting

  

Pivoting adalah bergerak dari satu temuan menuju temuan lain menggunakan field yang sama atau berkaitan.

  

Contoh arah pivot:

  

- **User** → cari seluruh aktivitas user tersebut.

- **IP** → cari host dan login yang berasal dari IP tersebut.

- **Process** → cari parent process, child process, command line, dan aktivitas jaringan terkait.

- **Hostname** → cari semua event yang tercatat pada host tersebut.

- **Timestamp** → cari event lain dalam rentang waktu yang berdekatan.

  

| Titik awal | Pivot berikutnya |

|---|---|

| User | IP, host, process, group |

| IP | user, host, destination |

| Process | parent, child, command line |

| Service | image path, account, creator |

| Task | action, creator, execution |

| Timestamp | event sebelum dan sesudah |

## 13. Correlation

  

Correlation adalah menghubungkan lebih dari satu evidence menjadi satu gambaran yang lebih utuh. Dasar korelasi yang umum dipakai:

  

- same user

- same IP

- same host

- same process

- same session

- same Logon ID

- same time window

- hubungan sebab-akibat yang masuk akal

  

**Contoh fiktif:**

  

```

19:55 — beberapa login gagal

20:01 — login berhasil

20:03 — privilege meningkat

20:05 — PowerShell dijalankan

20:09 — service baru muncul

```

  

Satu event hanya menunjukkan satu aktivitas tunggal. Beberapa event yang berurutan dan saling berkaitan dapat menunjukkan sebuah pola. Namun, jangan langsung menyebutnya sebagai *attack chain* sebelum melalui proses verifikasi.

  

Pertanyaan verifikasi sebelum menyimpulkan korelasi:

  

- Apakah user-nya sama?

- Apakah host-nya sama?

- Apakah IP-nya sama?

- Apakah urutan waktunya masuk akal?

- Apakah proses-prosesnya saling berhubungan?

- Apakah ada bukti yang justru bertentangan dengan pola ini?

- Apakah aktivitas ini bisa dijelaskan oleh aktivitas administrasi normal?

## 14. Fakta, Indikasi, Dugaan, dan Kesimpulan

  

- **FAKTA** — data yang terlihat langsung pada evidence.

- **INDIKASI** — pola yang patut diperiksa lebih lanjut.

- **DUGAAN** — hipotesis yang belum cukup didukung bukti.

- **KESIMPULAN** — pernyataan yang didukung oleh beberapa evidence.

  

**Contoh:**

  

- FAKTA: Terdapat event login gagal untuk akun administrator pada pukul tertentu.

- INDIKASI: Terjadi beberapa login gagal dalam waktu yang singkat.

- DUGAAN: Aktivitas tersebut mungkin merupakan percobaan brute force.

- KESIMPULAN: Dapat disebut brute force hanya jika frekuensi, sumber, pola waktu, dan konteks lain benar-benar mendukung.

  

> **WAJIB PAHAM**

> Jangan menaikkan Dugaan menjadi Kesimpulan tanpa bukti tambahan yang mendukung.

## 15. Hipotesis Investigasi

  

Alur pembentukan hipotesis:

  

```

Observation → Hypothesis → Test → Result → Refine or Reject

```

  

**Contoh:**

  

- Observation: Banyak login gagal.

- Hypothesis: Satu IP mencoba menebak password.

- Test: Kelompokkan event berdasarkan source IP dan username.

- Result: Jika ternyata berasal dari banyak IP internal dan user yang berbeda-beda, hipotesis awal mungkin perlu ditinjau ulang.

  

Hipotesis boleh salah — tujuannya adalah memandu pencarian, bukan memaksa evidence agar sesuai dengan dugaan awal.

  

**Template hipotesis:**

  

```

Observation        :

Hypothesis          :

Data yang diperlukan:

Filter/pivot        :

Hasil                :

Status hipotesis     : Diterima sementara / Ditolak / Belum cukup bukti

```

## 16. False Positive dan Konteks

  

False positive adalah aktivitas yang terlihat mencurigakan tetapi memiliki penjelasan normal.

  

> **FALSE POSITIVE**

> Contoh umum: banyak login gagal karena password lama masih tersimpan di suatu aplikasi; service baru berasal dari software resmi yang baru dipasang; PowerShell dijalankan oleh administrator untuk kebutuhan rutin; event log dibersihkan saat jadwal maintenance; akun baru dibuat untuk kebutuhan operasional.

  

Aktivitas yang tampak normal pun tetap harus diverifikasi, bukan langsung diasumsikan aman.

  

Checklist konteks:

  

- Apakah waktu kejadian sesuai jam kerja?

- Apakah user yang terlibat memang administrator?

- Apakah file terkait memiliki signature yang sah?

- Apakah aktivitas tercatat pada change request?

- Apakah ada event lanjutan yang mencurigakan?

- Apakah sumber IP dikenal?

- Apakah aktivitas ini terjadi berulang secara wajar?

  

---

  

## 17. Confidence Level

  

Gunakan sistem sederhana berikut untuk menilai seberapa kuat sebuah temuan:

  

- **LOW** — hanya satu evidence, konteks minim.

- **MEDIUM** — beberapa evidence mendukung, tetapi masih ada penjelasan alternatif yang masuk akal.

- **HIGH** — beberapa evidence independen saling mendukung dan tidak ada kontradiksi berarti.

  

**Format findings:**

  

```

Finding                :

Evidence                :

Interpretation           :

Confidence                : Low / Medium / High

Alternative explanation   :

Next verification          :

```

  

Confidence di sini bukan angka persentase matematis, melainkan penilaian kualitatif berdasarkan seberapa kuat evidence yang mendukung.

  

---

  

## 18. Raw Event versus Parsed Output

  

Parsed output (CSV, tabel SIEM) membantu pencarian cepat. Raw event digunakan untuk verifikasi akhir.

  

```

CSV/SIEM

  → temukan event menarik

    → buka raw event

      → verifikasi field

        → screenshot

          → catat findings

```

  

Risiko yang perlu diwaspadai pada parser:

  

- Field dapat berpindah posisi dibanding tampilan aslinya.

- Nama kolom bisa dinormalisasi sehingga berbeda dari nama field asli.

- Sebagian data bisa ikut masuk ke satu kolom gabungan seperti Payload.

- Tidak semua event memiliki struktur field yang sama.

- Parser yang berbeda bisa menggunakan mapping field yang berbeda pula.

  

> **COMBAT RULE**

> Gunakan parser untuk mencari, gunakan raw event untuk memastikan.

## 19. Dokumentasi Investigasi

  

Ada tiga jenis catatan yang perlu dibedakan:

  

- **Working Notes** — catatan yang ditulis selama investigasi berjalan.

- **Findings** — temuan yang sudah memiliki evidence pendukung.

- **Write-up** — dokumentasi final yang menjelaskan proses dan jawaban secara menyeluruh.

  

**Format working notes:**

  

```

Case ID           :

Objective          :

Start time          :

Evidence             :

Timezone              :

Tools                  :

Queries/filters          :

Interesting events         :

Open questions               :

Next pivot                     :

```

  

**Format findings:**

  

```

Finding ID   :

Timestamp     :

User           :

Host             :

IP                :

Process             :

Evidence               :

Interpretation            :

Confidence                   :

Screenshot                      :

```

## 20. Screenshot Evidence

  

Screenshot yang baik menampilkan:

  

- Nama tool yang dipakai.

- Event atau baris data yang relevan.

- Timestamp.

- Event ID atau field utama yang menjadi fokus.

- Konteks secukupnya (tidak terlalu sempit, tidak terlalu luas).

- Tidak terlalu banyak area kosong.

- Tidak memotong field penting di tepi layar.

- Nama file yang konsisten dengan konvensi penamaan.

  

Contoh penamaan:

  

```

H1-LAB-01_01_EVENT_OVERVIEW.png

H1-LAB-01_02_SUBJECT_TARGET.png

H1-LAB-01_03_TIMELINE.png

```

  

> **BUKTI LOMBA**

> Screenshot bukan satu-satunya evidence yang perlu disimpan. Simpan juga query, filter, dan findings yang menyertainya — screenshot tanpa catatan sulit ditelusuri ulang.

  

---

  

## 21. Cara Menjawab Soal

  

Alur menjawab soal:

  

1. Baca objective secara utuh.

2. Tandai format jawaban yang diminta.

3. Identifikasi evidence yang relevan.

4. Temukan event utama.

5. Verifikasi field pada raw event.

6. Cari event pendukung bila diperlukan.

7. Simpan screenshot.

8. Tulis jawaban.

9. Periksa kapitalisasi dan satuan waktu/timezone pada jawaban.

10. Submit jawaban.

11. Perbarui write-up.

  

Beberapa aturan penting:

  

- Jawab hanya apa yang diminta soal.

- Jangan menambahkan asumsi ke dalam flag atau jawaban.

- Jangan mengubah format jawaban yang sudah ditentukan.

- Jangan lupa satuan waktu bila jawaban berupa timestamp.

- Jangan menyalin spasi tambahan saat menempelkan jawaban.

  

---

  

## 22. Manajemen Waktu Kompetisi

  

Pembagian waktu yang disarankan per soal (bersifat panduan, bukan aturan mutlak):

  

| Rentang waktu | Aktivitas |

|---|---|

| 0–3 menit | Baca objective dan format jawaban |

| 3–8 menit | Triage evidence yang tersedia |

| 8–20 menit | Filter dan pivot |

| 20–30 menit | Correlation dan verification |

| menit ke-30 | Putuskan lanjut atau pindah soal |

  

Prinsip urutan pengerjaan:

  

```

EASY FIRST → MEDIUM → HARD → RETURN

```

  

Aturan tambahan:

  

- Jangan menghabiskan waktu terlalu lama pada satu filter yang tidak membuahkan hasil.

- Simpan bukti begitu ditemukan, jangan ditunda.

- Tulis findings sambil berjalan, bukan di akhir sesi.

- Jika buntu, catat posisi terakhir sebelum berpindah.

- Pindah ke soal lain tanpa kehilangan konteks soal sebelumnya.

## 23. Decision Point Ketika Buntu

  

**Tidak ada hasil:**

  

```

Tidak ada hasil

  → cek time range

    → cek timezone

      → cek field

        → kurangi filter

          → buka raw event

            → ganti tool

              → cari pivot lain

                → dokumentasikan

                  → pindah sementara

```

  

**Event terlalu banyak:**

  

```

Event terlalu banyak

  → tambahkan waktu

    → tambahkan user/host/IP

      → kelompokkan

        → cari outlier

          → prioritaskan objective

```

  

**Temuan bertentangan:**

  

```

Temuan bertentangan

  → periksa raw data

    → periksa timezone

      → periksa host berbeda

        → periksa user berbeda

          → turunkan confidence

            → jangan simpulkan dulu

```

## 24. Kesalahan Umum Pemula

  

| Kesalahan | Dampak | Perbaikan |

|---|---|---|

| Langsung mencari jawaban tanpa membaca objective | Waktu terbuang untuk arah yang salah | Pecah objective dengan WHO–WHAT–WHEN–WHERE–HOW–PROOF dulu |

| Menganggap satu event sudah cukup | Kesimpulan terlalu dini dan mudah salah | Cari event pendukung sebelum menyimpulkan |

| Menganggap semua aktivitas aneh adalah serangan | False positive dianggap benar | Periksa checklist konteks sebelum menyimpulkan |

| Mengabaikan timezone | Jawaban waktu salah | Catat timezone sebelum menjawab pertanyaan berbasis waktu |

| Salah membedakan Subject dan Target | Jawaban tertukar antara pelaku dan sasaran | Verifikasi field pada raw event, jangan menebak dari posisi tampilan |

| Tidak menyimpan query | Sulit mengulang langkah bila diminta verifikasi ulang | Catat query/filter pada working notes setiap kali dipakai |

| Tidak menyimpan screenshot | Findings tidak punya bukti visual | Simpan screenshot begitu event penting ditemukan |

| Menganalisis ORIGINAL | Evidence asli berisiko rusak atau berubah | Selalu analisis WORKING, bukan ORIGINAL |

| Mengubah nama evidence tanpa catatan | Sulit menelusuri asal file | Catat nama asli dan sumber setiap file |

| Mengarang data yang tidak terlihat | Jawaban tidak valid dan berisiko fatal | Jawab hanya berdasarkan apa yang benar-benar terlihat pada evidence |

| Menyamakan event absence dengan aktivitas tidak terjadi | Kesimpulan keliru | Periksa dulu time range, filter, dan log source sebelum menyimpulkan tidak ada aktivitas |

| Membuka Answer Key terlalu awal | Proses berpikir investigasi tidak terbentuk | Selesaikan proses investigasi dulu sebelum melihat kunci jawaban |

| Menulis write-up setelah semua soal selesai | Detail penting terlupa | Tulis working notes dan findings sambil berjalan |

| Terlalu bergantung pada satu tool | Kehilangan konteks saat tool tidak menunjukkan hasil | Biasakan verifikasi silang dengan raw event atau sumber lain |

| Tidak memeriksa raw event | Salah interpretasi field hasil parsing | Gunakan parser untuk mencari, raw event untuk memastikan |

## 25. Mini Practice Tanpa Evidence

  

Latihan konsep berikut tidak memerlukan evidence — tujuannya melatih pola pikir sebelum masuk ke Windows Event Log.

  

1. Pecah objective berikut dengan WHO–WHAT–WHEN–WHERE–HOW–PROOF: *"Tentukan siapa yang mengubah keanggotaan sebuah grup administratif pada suatu host dalam rentang waktu tertentu."*

2. Sebuah file diterima dari INBOX. Jelaskan ke folder mana file itu pertama kali disalin, dan ke folder mana salinan kerja dibuat.

3. Pernyataan *"Ditemukan beberapa login gagal dari satu IP yang sama dalam waktu singkat"* termasuk fakta atau dugaan? Jelaskan alasannya.

4. Sebuah event tercatat pada 03:00 UTC. Berapa waktu tersebut dalam WIB?

5. Dari sebuah username yang ditemukan pada satu event, sebutkan dua arah pivot berikutnya yang paling masuk akal.

6. Sebuah temuan hanya didukung oleh satu event tanpa konteks tambahan. Confidence level apa yang paling tepat untuk temuan ini?

  

### Cek Jawaban Konseptual

  

Nomor 1 melatih kebiasaan memecah objective sebelum membuka tool apa pun — perhatikan bahwa WHAT di sini adalah perubahan keanggotaan grup, bukan pembuatan user baru.

  

Nomor 2 menegaskan urutan evidence handling: file dari INBOX pertama kali disalin ke ORIGINAL, baru kemudian salinan kerja dibuat di WORKING.

  

Nomor 3 melatih kepekaan terhadap level fakta — "beberapa login gagal dari IP yang sama" adalah pola yang teramati langsung sehingga tergolong fakta/indikasi, bukan dugaan; dugaan baru muncul ketika pola itu diberi label seperti "brute force".

  

Nomor 4 melatih konversi dasar UTC ke WIB dengan offset +7 jam.

  

Nomor 5 melatih arah pivot dari username, misalnya ke IP yang dipakai user tersebut atau ke host tempat user itu aktif.

  

Nomor 6 melatih penilaian confidence — satu evidence tanpa konteks tambahan berada pada level LOW.
